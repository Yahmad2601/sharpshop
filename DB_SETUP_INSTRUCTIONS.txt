DATABASE SETUP INSTRUCTIONS
===========================

DEPLOYMENT / ENV NOTES
----------------------
- Express login sessions are now Postgres-backed via connect-pg-simple when
  DATABASE_URL is set (see the frontend .env). The "session" table is created
  automatically on first boot. Without DATABASE_URL it falls back to in-memory
  (logins reset on restart). Set DATABASE_URL in production.
- Flutterwave webhook: set FLUTTERWAVE_SECRET_HASH (root .env) to any secret,
  paste the same value into the Flutterwave dashboard webhook settings, and
  point the webhook URL at  https://<python-backend>/api/webhook/flutterwave
- KNOWN LIMITATION (not yet done): the Python customer-chat sessions
  (customer_sessions.py) and WhatsApp seller sessions (server.py user_sessions)
  are still in-memory dicts. They survive within one running process but reset
  on restart and do NOT share across multiple Python dynos. Single-dyno
  deployments are unaffected; move these to Redis/Postgres before scaling the
  Python backend horizontally.

To enable the Payment and Fulfillment flow for the Customer Agent, the following database changes are required in Supabase.

Please execute the following SQL script in the Supabase SQL Editor:

```sql
-- Create orders table if it doesn't exist
CREATE TABLE IF NOT EXISTS orders (
  id UUID DEFAULT gen_random_uuid() PRIMARY KEY,
  trader_id TEXT NOT NULL REFERENCES traders(id),
  product_id UUID NOT NULL REFERENCES products(id),
  amount NUMERIC NOT NULL,
  currency TEXT DEFAULT 'NGN',
  fulfillment_type TEXT CHECK (fulfillment_type IN ('delivery', 'pickup')),
  delivery_details JSONB,
  status TEXT DEFAULT 'pending' CHECK (status IN ('pending', 'paid', 'failed', 'fulfilled')),
  payment_ref TEXT,
  created_at TIMESTAMP WITH TIME ZONE DEFAULT timezone('utc'::text, now()) NOT NULL
);

-- Enable RLS
ALTER TABLE orders ENABLE ROW LEVEL SECURITY;

-- create Policies (Adjust as needed for production security)
CREATE POLICY "Allow public insert on orders" ON orders FOR INSERT WITH CHECK (true);
CREATE POLICY "Allow public select on orders" ON orders FOR SELECT USING (true);
CREATE POLICY "Allow public update on orders" ON orders FOR UPDATE USING (true);
```

Once this table is created, the Agent will be able to generate orders and payment links successfully.

PAYMENT CONFIRMATION FUNCTION (required)
----------------------------------------
The backend calls this RPC when Flutterwave confirms a payment. It marks the
order paid and decrements product stock in ONE transaction (row-locked), so
two concurrent buyers cannot both take the last item. Run this in the
Supabase SQL Editor:

```sql
CREATE OR REPLACE FUNCTION confirm_order_paid(p_order_id UUID)
RETURNS TEXT
LANGUAGE plpgsql
SECURITY DEFINER
AS $$
DECLARE
  v_order orders%ROWTYPE;
  v_rows INT;
BEGIN
  SELECT * INTO v_order FROM orders WHERE id = p_order_id FOR UPDATE;
  IF NOT FOUND THEN
    RETURN 'order_not_found';
  END IF;
  IF v_order.status = 'paid' THEN
    RETURN 'already_paid';
  END IF;

  UPDATE products
     SET stock_quantity = stock_quantity - 1
   WHERE id = v_order.product_id
     AND stock_quantity > 0;
  GET DIAGNOSTICS v_rows = ROW_COUNT;

  UPDATE orders
     SET status = 'paid',
         payment_ref = 'sharpshop_' || p_order_id::text
   WHERE id = p_order_id;

  IF v_rows = 0 THEN
    -- Payment received but stock was already 0: order is still marked paid,
    -- flag it for manual follow-up/refund.
    RETURN 'paid_out_of_stock';
  END IF;
  RETURN 'paid';
END;
$$;
```

If the function is missing, the backend falls back to non-atomic updates and
logs a warning — deploy the function to get correct concurrent behavior.

LIKE / FAVORITE DEDUPLICATION (recommended)
-------------------------------------------
The API checks for an existing row before inserting, but only a DB constraint
makes this race-proof. Dedupe first, then add the constraints:

```sql
DELETE FROM likes a USING likes b
WHERE a.ctid < b.ctid AND a.product_id = b.product_id AND a.user_id = b.user_id;
ALTER TABLE likes ADD CONSTRAINT likes_product_user_unique UNIQUE (product_id, user_id);

DELETE FROM favorites a USING favorites b
WHERE a.ctid < b.ctid AND a.product_id = b.product_id AND a.user_id = b.user_id;
ALTER TABLE favorites ADD CONSTRAINT favorites_product_user_unique UNIQUE (product_id, user_id);
```

TIMESTAMP COLUMNS (recommended)
-------------------------------
Several tables store created_at as TEXT ("2026-07-01 12:34:56"), a format
new Date() cannot parse in every browser. The frontend now guards against
this, but converting the columns to real timestamps fixes it at the source
(timestamptz serializes as ISO 8601 with a timezone):

```sql
ALTER TABLE comments  ALTER COLUMN created_at TYPE timestamptz USING created_at::timestamptz;
ALTER TABLE favorites ALTER COLUMN created_at TYPE timestamptz USING created_at::timestamptz;
ALTER TABLE likes     ALTER COLUMN created_at TYPE timestamptz USING created_at::timestamptz;
ALTER TABLE users     ALTER COLUMN created_at TYPE timestamptz USING created_at::timestamptz;
ALTER TABLE traders   ALTER COLUMN created_at TYPE timestamptz USING created_at::timestamptz;
```

(Skip any table whose created_at is already a timestamp type.)

RECOMMENDED CLEANUP JOB (optional)
----------------------------------
Abandoned pending orders (customer never paid) should be swept periodically.
In Supabase you can schedule this with pg_cron, or run it manually:

```sql
UPDATE orders SET status = 'failed'
WHERE status = 'pending'
  AND created_at < now() - interval '24 hours';
```
